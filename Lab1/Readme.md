# GNSS Single Point Positioning (SPP) Analysis Pipeline

A comprehensive toolkit for processing GNSS UBX data files and performing Single Point Positioning (SPP) analysis with weighted least squares estimation.

---

## Quick Start

The commands below give a runnable entry point; the lab report, submission, ranking and AI-use rules of the course are described further down this page.
Step-by-step instructions are in [docs/RUNNING.md](docs/RUNNING.md) and the data sources in [docs/DATA_SOURCES.md](docs/DATA_SOURCES.md).
Run all commands from the `Lab1` folder of this repository. The numerical Python entry point only needs NumPy.

```powershell
python -m pip install -r requirements.txt
python WLSE_spp.py --reference dataset/NAV-HPPOSECEF.csv
python tools/check_submission.py outputs/example/G01_owndata.csv --epoch-file dataset/epochs.csv
python WLSE_spp.py --mode gps --input-dir benchmark/preprocessed_gps --output-dir outputs/benchmark --submission G01_benchmark.csv
python tools/check_submission.py outputs/benchmark/G01_benchmark.csv --week 2158 --epoch-file benchmark/preprocessed_gps/epochs.csv
```

- **Example dataset**: 186/186 epochs; reproduces the 2D/3D RMS differences of the slides (37.910758/51.042844 m). The comparison is against the receiver solution, not a ground truth.
- **Benchmark GPS baseline**: 1437/1534 epochs solved from the GPS input cache generated from the included OBS/NAV files (availability 93.6767 %). Passing the count and format checks says nothing about accuracy or rank.
- `dataset/` holds the 186-epoch example; `benchmark/` holds the 1534-epoch UrbanNav observations and the cleaned navigation file; `benchmark/preprocessed_gps/` lets you run Python without MATLAB.
- `historical` mode only reproduces the archived example numbers; `gps` mode is a GPS L1 baseline without multi-constellation extensions. The report, improvement and analysis requirements below still apply.
- `G01` is a demonstration group number; use your own group number. The example `G01_owndata.csv` is not your own field data.
- The PDFs, report template, third-party toolbox and workflow figures are the course originals; the figures are not regenerated by the command-line entry point.
- The checker enforces the exact header, 3-decimal coordinates, finite values and time order, and also checks the group file name and that the position lies near the Earth's surface. The online platform remains the final authority for acceptance and scoring.

## Overview

This pipeline provides a complete workflow for GNSS data processing, from raw UBX file collection to advanced positioning analysis with error evaluation. The workflow includes data collection, data conversion, visualization, and statistical analysis of positioning accuracy.

**New in 2026/27:** (i) an urban benchmark dataset from UrbanNav, (ii) a CSV submission ranked on a class leaderboard by horizontal RMSE, and (iii) explicit permission to use generative AI tools for coding, subject to the rules in the tutorial (Section 3.3).

## Workflow Overview

The complete pipeline consists of four main steps:

![Lab1 Workflow](examples/flow.png)

## Step 0: GNSS Data Collection
For detailed GNSS data collection procedures, please refer to Section 5 of the [AAE4203_26_27_S1_Lab_Tutorial.pdf](AAE4203_26_27_S1_Lab_Tutorial.pdf). Log 15–20 minutes of static data near Block X and name the file e.g. `G05_owndata_20261030.ubx`.

## Step 1: UBX to RINEX Conversion

### 1.1 Using rtkconv

1. Launch RTKconv from RTKLIB
2. Load your UBX file as input
3. Configure output settings:
   - Format: RINEX
   - Generate both observation (.obs) and navigation (.nav) files
4. Run conversion to generate RINEX files

### 1.2 Generate Reference Solution

1. Launch RTKPOST from RTKLIB
2. Load the generated RINEX observation and navigation files
3. Configure positioning mode (typically SPP for reference)
4. Generate reference positioning solution for accuracy comparison

## Step 2: RINEX Data Processing

### 2.1 Select Input and Output Paths

No source-code editing is needed. In MATLAB, with `Lab1` as the current folder:

```matlab
% The provided benchmark, GPS L1 baseline:
rinex2csv('benchmark/UrbanNav-HK-Deep-Urban-1.ublox.f9p.obs', ...
          'benchmark/UrbanNav_20210521_multiGNSS_clean.nav', ...
          'outputs/benchmark_inputs');
```

### 2.2 Run on Your Own Data

```matlab
rinex2csv('mydata/my.obs','mydata/my.nav','outputs/own_inputs');
```

The arguments are `(observation_file, navigation_file, output_directory)`.
The original course script is retained in `legacy/rinex2csv_course_original.m` for reference; do not run the new function with `run(...)`.
For regenerating the historical example as a new GPS-only solution, use the paired `dataset/COM6___9600_250916_020025_blockz.obs` and `.nav` and a separate output directory. This produces 113/186 usable epochs under the new masks, rather than the historical 186-epoch CSV regression.

### 2.3 Outputs and Reference Visualizations

### 2.4 Generated CSV Files

The following CSV files will be created for subsequent processing:
- `pseudoranges_meas.csv` - Raw pseudorange measurements
- `satellite_clock_bias.csv` - Satellite clock corrections
- `ionospheric_delay.csv` - Ionospheric delay corrections
- `tropospheric_delay.csv` - Tropospheric delay corrections
- `satellite_positions.csv` - Computed satellite positions
- `epochs.csv` - Actual GPS week and time of week, one row per measurement epoch
- `group_delay.csv`, `elevation_deg.csv`, `satellites.csv` - GPS TGD, selected elevations and satellite identifiers

The five measurement matrices use one column per epoch (three adjacent columns for each satellite-position epoch). Keep all files from the same conversion together.

## Step 3: UBX to CSV Conversion

### 3.1 Install Dependencies

Ensure pyubx2 is installed:

```bash
pip install pyubx2
```

### 3.2 Run GUI Converter

Execute the Python GUI converter:

```bash
python pyubx2_csv_converter_gui.py
```

### 3.3 Using the GUI

1. **Select Input UBX File**: Browse and select your raw UBX data file
2. **Choose Output Directory**: Select where to save the converted CSV files
3. **Start Conversion**: Click "Start" to begin the conversion process

The GUI provides:
- Real-time progress indication
- Background processing to keep UI responsive
- Error handling and status updates

### 3.4 Key Output: Receiver Reference Solution

The conversion generates `NAV-HPPOSECEF.csv`, which contains the receiver's own high-precision ECEF solution. Without RTK corrections this is a standalone real-time solution that can be wrong by several metres in an urban canyon: use it as a reference for comparison, not as ground truth. Accuracy against a true trajectory is measured only on the benchmark dataset.

## Step 4: SPP Analysis

### 4.1 Choose the Processing Mode

`WLSE_spp.py` accepts explicit input/output directories. It never needs UrbanNav ground truth.
`--reference` optionally compares a receiver CSV after positioning; it is not an input to the positioning solution.

### 4.2 Run SPP Analysis

Historical CSV regression (matches the supplied 186-epoch results):

```powershell
python WLSE_spp.py --reference dataset/NAV-HPPOSECEF.csv
```

GPS benchmark from the included measurement cache:

```powershell
python WLSE_spp.py --mode gps --input-dir benchmark/preprocessed_gps --output-dir outputs/benchmark --submission G05_benchmark.csv
```

After regenerating the benchmark in Step 2, replace the input directory with `outputs/benchmark_inputs`.
After converting your own measurements:

```powershell
python WLSE_spp.py --mode gps --input-dir outputs/own_inputs --output-dir outputs/own --submission G05_owndata.csv
```

Replace `G05` with your group number. Do not submit the historical example as your own field collection.

### 4.3 Algorithm Features and Limits

- Historical mode preserves the original numerical functions and supplied CSVs for regression; those CSVs do not identify constellations.
- GPS mode uses one receiver clock, elevation weighting, atmospheric and satellite-clock corrections, separate TGD correction, and Earth-rotation range correction.
- New RINEX conversion is GPS-only. Multi-constellation methods remain a student extension, not a feature claimed for this baseline.
- Failed epochs are omitted and logged, never filled with the preceding position. Check availability separately from accuracy.
- Modern outputs are standard five-column submissions, detailed ECEF solutions, omitted-epoch reasons and a summary JSON; see Output Files.

For numerical regression, malformed-CSV checks, missing-epoch checks and package integrity:

```powershell
python tools/verify_package.py
```

Step-by-step instructions: [docs/RUNNING.md](docs/RUNNING.md). Verification results and limitations: [docs/VERIFICATION.md](docs/VERIFICATION.md).

## Step 5: Accuracy Challenge and Leaderboard

Process the UrbanNav benchmark dataset with your best algorithm and submit one position per epoch. Verify every new version on the example dataset first.

### 5.1 CSV File Format

One header line, then one row per benchmark epoch in time order. Positions are WGS-84 ECEF coordinates in metres; no latitude/longitude and no extra columns.

| Column | Meaning | Unit / format |
|--------|---------|---------------|
| `gps_week` | GPS week number | integer |
| `gps_tow_s` | GPS time of week of the epoch | s, at least 1 decimal |
| `x_ecef_m` | Estimated receiver position, ECEF X | m, 3 decimals |
| `y_ecef_m` | Estimated receiver position, ECEF Y | m, 3 decimals |
| `z_ecef_m` | Estimated receiver position, ECEF Z | m, 3 decimals |

```text
gps_week,gps_tow_s,x_ecef_m,y_ecef_m,z_ecef_m
2158,455346.0,-2418202.586,5385847.524,2405648.799
2158,455347.0,-2418202.174,5385847.238,2405648.952
```

File names: `GXX_benchmark.csv` and `GXX_owndata.csv`, where `XX` is your two-digit group number (G01–G20).

### 5.2 Check and Upload

```bash
python tools/check_submission.py G05_benchmark.csv --week 2158 --epoch-file benchmark/preprocessed_gps/epochs.csv
```

For own-data CSVs, use `--epoch-file outputs/own_inputs/epochs.csv` without the benchmark `--week` option. The one-file checker invocation without options also remains supported for format-only checks. `--epochs 1534` estimates count coverage; `--epoch-file` checks membership against actual OBS times. A format pass is not an accuracy assessment.

Fix all errors, then upload both CSV files to your group's sub-folder in the TA's Google Drive folder (link on Blackboard). Replace the file whenever you have a better solution; only the latest `GXX_benchmark.csv` at the deadline is used for the final ranking. The leaderboard platform source code is available at [PolyU-TASLAB/AAE4203_ASN_2026](https://github.com/PolyU-TASLAB/AAE4203_ASN_2026).

### 5.3 Ranking Rules

- Errors are computed in the local East-North-Up frame at the ground-truth position, for epochs matched by GPS week and time of week (to 0.1 s).
- Only submissions with availability ≥ 90 % are ranked.
- Ranked submissions are ordered by 2D RMSE (smaller is better); ties are broken by 3D RMSE. The leaderboard also reports the 95th-percentile 2D error and availability.
- Your repository must reproduce the submitted file; the teaching team may re-run the code of any group.

## Troubleshooting

### Common Issues

#### MATLAB Issues
- **matRTKLIB not found**: Ensure the matRTKLIB directory is added to MATLAB path
- **File path errors**: Use absolute paths or ensure files are in MATLAB working directory
- **Memory issues**: For large datasets, consider processing in smaller segments

#### Python Issues
- **pyubx2 import error**: Install using `pip install pyubx2`
- **plotting dependencies**: the numerical CLI needs only NumPy; Cartopy is not required
- **CSV file not found**: Verify file paths and ensure Step 2 completed successfully

#### Data Quality Issues
- **Insufficient satellites**: Check SNR thresholds and elevation angle masks
- **Poor positioning accuracy**: Verify correction models and satellite geometry
- **Conversion failures**: Ensure UBX files are valid and not corrupted

### Performance Optimization

#### For Large Datasets
- Process data in segments if memory becomes an issue
- Adjust visualization parameters for better performance
- Consider using more restrictive satellite selection criteria

#### Accuracy Improvements
- Adjust SNR and elevation angle thresholds
- Fine-tune weighting functions
- Consider additional error correction models

## Technical Notes

### Coordinate Systems
- **ECEF**: Earth-Centered, Earth-Fixed coordinates
- **LLA**: Latitude, Longitude, Altitude
- **ENU**: East, North, Up local coordinate system

### Error Correction Models
- Ionospheric delay correction using broadcast parameters
- Tropospheric delay using standard atmospheric models
- Satellite clock corrections from navigation message
- Elevation-angle dependent weighting for measurement quality

### Algorithm Convergence
- Historical Python regression: up to 10 iterations, 1e-4 m position-update tolerance, with the preserved unweighted fallback.
- GPS Python mode: up to 30 iterations, 1e-4 m state-update tolerance, rank/convergence/surface checks and explicit omission on failure.
- MATLAB conversion: provisional GPS position and atmospheric iteration; convergence threshold 1e-3 m. These settings define a teaching baseline, not an accuracy guarantee.
